# Техническое задание: Somon Rent Watcher

**Статус:** draft v1 — достаточно определён для реализации MVP  
**Дата разведки:** 2026-09-01  
**Цель:** мониторить свежие объявления об аренде квартир в Душанбе на Somon.tj и отправлять в заданную Telegram-группу только объявления, подходящие под настраиваемый фильтр.

---

## 1. Основные принципы

Проект намеренно строится по KISS:

- Go;
- обычные HTTP GET без браузера;
- HTML-парсинг;
- SQLite;
- Telegram Bot API;
- один процесс;
- без Firecrawl;
- без Playwright/Selenium/Chromium;
- без внутреннего API Somon;
- без LLM/AI/NLP;
- без прокси, CAPTCHA bypass и антибот-обходов;
- без Redis, PostgreSQL, очередей и Docker как обязательной части;
- без сложных эвристик распознавания объявлений.

Система предназначена именно для **fresh-only мониторинга**, а не для полного архива Somon.

## 2. Результаты технической разведки Somon.tj

### 2.1. Основная выдача

Основной URL:

`https://somon.tj/nedvizhimost/arenda-kvartir/dushanbe/`

На момент разведки страница сообщала примерно 4.3 тыс. объявлений аренды квартир в Душанбе.

Обычный HTTP-ответ страницы уже содержит первоначальный набор карточек — запуск JavaScript для их получения не требуется.

В исследованном снимке было:

- 16 карточек VIP;
- 10 карточек TOP;
- 34 обычных карточки;
- всего 60 карточек.

После 60-й карточки серверный документ переходил к блоку «Объявления ... в других городах».

**Важно:** число 60 и пропорция 16/10/34 — наблюдаемое текущее поведение, а не контракт. Код не должен зависеть от фиксированного количества карточек.

В обычной части исследованного снимка 34 карточки покрывали период от нескольких минут до нескольких часов, что даёт большой запас при опросе раз в 10–30 минут.

### 2.2. Что доступно прямо из карточки списка

Из карточки основной выдачи можно получить без открытия detail-page:

- ссылку на объявление;
- ID из URL `/adv/<ID>_...`;
- заголовок;
- количество комнат из заголовка;
- этаж из заголовка;
- текущую цену;
- первую фотографию;
- отображаемый возраст объявления;
- признак VIP;
- признак TOP;
- иногда имя автора.

Типовая форма заголовка:

`2-комн. квартира, 8 этаж, 69м², ...`

Это позволяет делать дешёвый предварительный фильтр до дополнительного GET страницы объявления.

### 2.3. Detail-page

Обычная страница объявления `/adv/...` сервером отдаёт без браузера:

- видимый ID;
- заголовок;
- точный этаж;
- цену;
- описание;
- фотографии;
- имя автора;
- срок присутствия автора на сайте;
- количество активных объявлений автора.

Проверенный пример содержал:

`1 активное объявление`

Другой проверенный пример:

`17 активных объявлений`

Поэтому переходить на отдельную страницу `/author/` для получения количества объявлений автора **не требуется**.

### 2.4. URL slug нельзя считать источником характеристик

В одном живом объявлении URL содержал старое значение этажа (`12-etazh`), тогда как видимый заголовок и detail-page показывали `4 этаж`.

Следовательно:

- ID из URL использовать можно;
- комнаты, этаж, площадь и прочие поля из URL slug извлекать нельзя;
- источником характеристик является только текущий HTML карточки/detail-page.

### 2.5. Цена со скидкой

Somon может показывать текущую и старую цену одновременно, например:

`5 999 c. 6 599 c.`

Парсер должен брать текущую цену из актуального DOM-элемента цены. Если DOM не позволяет однозначно различить цену, допустимый fallback — первое ценовое значение карточки, закреплённое fixture-тестом.

### 2.6. Продвигаемые объявления

На сайте отдельно встречаются метки:

- `VIP`;
- `ТОП`.

В интерфейсе нашего бота они объединяются в один пользовательский тип:

**VIP = любое продвигаемое объявление (VIP или TOP).**

`Обычное` = карточка без признака продвижения.

### 2.7. Lazy load

В браузере Somon может догружать дальнейшую выдачу, но MVP не должен исследовать или использовать скрытый механизм lazy load.

Причина: первоначального серверного набора достаточно для частого fresh-only мониторинга, а использование внутренних endpoint'ов усложнит и сделает решение хрупким.

### 2.8. Чистые подкатегории комнат

У Somon существуют обычные URL:

- `/nedvizhimost/arenda-kvartir/1-komnatnyie/dushanbe/`
- `/nedvizhimost/arenda-kvartir/2-komnatnyie/dushanbe/`
- `/nedvizhimost/arenda-kvartir/3-komnatnyie/dushanbe/`
- аналогичные URL для 4, 5 и 6+ комнат.

В нормальном режиме они **не опрашиваются**. Их можно использовать только как редкий recovery-механизм при обнаружении возможного разрыва ленты.

## 3. Ограничения robots.txt и правил Somon

### 3.1. robots.txt

На момент разведки robots.txt запрещал, среди прочего:

- `/api`
- `/profile`
- `*/author/`
- `/?page=`
- URL с `price_min`
- URL с `price_max`
- URL с `attrs__`
- `/mobile_search/`
- `/mobile_result/`

Основная категория аренды, обычные `/adv/...` и чистые подкатегории количества комнат в этом списке Disallow не указаны.

**Но robots.txt не является разрешением на автоматизированный сбор.**

### 3.2. Существенный compliance-риск

Текущий Лицензионный договор Somon содержит более жёсткие ограничения:

- п. 3.1.11 — использование базы предусмотрено через программные средства/интерфейс Somon; сторонние программы для доступа прямо не разрешаются;
- п. 3.4.7 — запрещаются извлечение, сбор, переработка и дальнейшее распространение информации других пользователей;
- п. 5.2 — использование базы иным способом без предварительного письменного разрешения запрещено.

Пользовательское соглашение также ограничивает сбор/копирование объектов вне предоставленного функционала.

Это означает, что **техническая реализуемость проекта однозначна, но production-эксплуатация собственного scraper'а конфликтует с опубликованными условиями Somon**.

До постоянного запуска желательно получить разрешение Somon либо отдельно принять решение по этому риску. Проект не должен содержать механизмы обхода блокировок или технических ограничений сайта.

## 4. Семантика «свежего объявления»

Для MVP используется максимально простое и надёжное определение:

> **Свежим считается ID объявления, который монитор ещё ни разу не видел после первоначальной baseline-инициализации.**

Следствия:

- повторный показ уже известного ID не отправляется;
- поднятие/обновление старого известного объявления не вызывает повторную отправку;
- изменение цены старого ID не вызывает повторную отправку;
- изменение фильтра не вызывает повторную проверку старых ID;
- если очень старое объявление раньше никогда не попадало в видимую ленту монитора, а затем было поднято и впервые увидено монитором, оно будет считаться новым для системы и может быть отправлено один раз.

Последний пункт — сознательный KISS-компромисс. Определять «истинную первоначальную дату создания» скрытыми методами не требуется.

## 5. Алгоритм опроса

### 5.1. Расписание

После каждого завершённого обычного цикла следующий цикл назначается через случайный интервал:

**10–30 минут, равномерное распределение.**

Средний интервал ≈ 20 минут.

Ожидаемая нагрузка основной страницы:

≈ 72 GET/сутки.

Никаких запросов каждую минуту.

### 5.2. Первый запуск

Если SQLite новая и baseline ещё не создан:

1. GET основной страницы аренды.
2. Распарсить все видимые карточки.
3. Все обнаруженные ID записать в `seen_ads`.
4. Сохранить snapshot обычной части выдачи.
5. **Ничего в Telegram не отправлять.**

После этого монитор сообщает только о впервые появившихся ID.

### 5.3. Нормальный цикл

1. GET основной страницы.
2. Проверить, что ответ похож на нормальную выдачу.
3. Распарсить карточки.
4. Разделить их на promoted и ordinary.
5. Найти ID, которых нет в `seen_ads`.
6. Для каждого нового ID применить дешёвый card-prefilter.
7. Если card-prefilter не пройден — записать ID как seen.
8. Если пройден — GET detail-page.
9. Применить detail-filter.
10. Если не пройден — записать ID как seen.
11. Если пройден — отправить объявление в Telegram.
12. Только после успешной отправки записать ID как seen.
13. Сохранить новый ordinary snapshot и время успешного poll.
14. Назначить следующий poll через random 10–30 минут.

Все detail-запросы выполняются последовательно. Worker pool не нужен.

## 6. Контроль возможного пропуска ленты

Полная математическая гарантия получения каждого объявления невозможна без полного обхода пагинации/внутренних endpoint'ов.

Для fresh-only режима используется лёгкая страховка.

### 6.1. Ordinary snapshot

После каждого успешного poll хранится список ID **только обычной части** выдачи.

VIP/TOP не используются для проверки continuity, потому что старые продвигаемые объявления могут долго оставаться на странице и скрывать факт обновления обычной ленты.

### 6.2. Gap suspicion

Recovery запускается, если выполняется хотя бы одно условие:

- текущий ordinary snapshot не имеет пересечения с предыдущим;
- сервис был остановлен/не мог успешно опрашивать сайт заметно дольше обычного интервала (ориентир: >45 минут).

Это эвристика, а не формальное доказательство пропуска.

### 6.3. Recovery

При gap suspicion:

1. отправить администратору техническое предупреждение;
2. однократно получить чистые страницы комнат, которые входят в текущий room-filter;
3. собрать оттуда неизвестные ID;
4. обработать их обычным pipeline;
5. вернуться к основному режиму.

Recovery не запускается на каждом poll.

Если фильтр включает `не указано`, отдельной room-page для этого значения нет; такие объявления восстанавливаются только из основной ленты.

## 7. Фильтры

Один бот обслуживает **один текущий глобальный фильтр** и одну целевую Telegram-группу.

### 7.1. Цена

Поля:

- `price_min` — optional;
- `price_max` — optional.

Границы включительные:

`min <= price <= max`

Допустимо:

- только min;
- только max;
- обе;
- без ограничения.

### 7.2. Количество комнат

Multi-select:

- `1к`
- `2к`
- `3к`
- `4к`
- `5к`
- `6+к`
- `не указано`

`6+к` = 6 комнат и больше.

Можно выбрать несколько значений.

Пустой набор не допускается.

### 7.3. Этаж

Multi-select:

- `1эт`
- `2эт`
- ...
- `13эт`
- `14+эт`
- `не указано`

`14+эт` = текущий этаж >= 14.

Можно выбрать несколько значений.

Пустой набор не допускается.

### 7.4. Количество активных объявлений автора

Single-select:

- `<2`
- `<5`
- `<10`
- `не важно`

Счётчик Somon включает текущее активное объявление, поэтому:

- `<2` фактически означает 1 активное объявление;
- `<5` = 1–4;
- `<10` = 1–9.

Если значение автора не удалось получить:

- при `не важно` объявление может пройти, в Telegram показать `не указано`;
- при активном числовом ограничении объявление фильтр не проходит.

Сложное распознавание «риелтор / собственник» не делается.

### 7.5. Негативные слова

Администратор задаёт список слов и/или фраз.

Перед поиском:

- текст переводится в lowercase;
- повторные пробелы схлопываются.

Проверяемая строка:

`title + "\n" + description`

Для каждого негативного выражения применяется обычный `strings.Contains`.

Если найдено хотя бы одно — объявление не проходит.

**Не использовать:**

- NLP;
- морфологический анализ;
- fuzzy matching;
- embeddings;
- LLM;
- синонимизацию;
- автоматическое исправление ошибок.

### 7.6. Тип объявления

Multi-select:

- `Обычные`
- `VIP`

Где `VIP` внутри системы = VIP + TOP Somon.

Можно включить оба.

## 8. Двухступенчатая фильтрация

### 8.1. Card-prefilter

Из карточки проверяются:

- цена;
- комнаты;
- этаж;
- ordinary/promoted.

Если объявление уже здесь не подходит, detail-page не запрашивается.

Комнаты:

простое извлечение из видимого заголовка, например regex по `N-комн`.

Этаж:

простое извлечение из видимого заголовка, например regex по `N этаж`.

Если поле не удалось получить — значение считается `unknown`, без дополнительных эвристик.

### 8.2. Detail-filter

Для прошедших card-prefilter выполняется один GET detail-page.

Получаются:

- описание;
- имя автора, если доступно;
- количество активных объявлений автора;
- первая/основная фотография;
- текущие отображаемые данные для дополнительной проверки.

Затем применяются:

- лимит активных объявлений автора;
- негативные слова.

Detail-page также используется как источник более надёжных текущих данных, если карточка и detail расходятся.

## 9. Работа с ошибками

### 9.1. HTTP client

Один переиспользуемый `http.Client`:

- keep-alive;
- timeout ориентировочно 15 секунд;
- последовательные запросы;
- один статический User-Agent;
- без fingerprint spoofing.

### 9.2. Network error / 5xx

- не делать немедленный retry-loop;
- записать ошибку в лог;
- дождаться следующего обычного цикла.

### 9.3. HTTP 403 / 429

- прекратить обычный polling;
- включить простой длинный backoff, например 2 часа;
- отправить предупреждение администратору;
- не использовать proxy rotation, CAPTCHA bypass или усиленное повторение запросов.

### 9.4. Parser sanity check

Если HTTP 200, но:

- не найдено ни одного корректного ad ID;
- количество карточек явно аномально мало для этой страницы (например <20);
- структура не похожа на ожидаемую,

считать это **ошибкой парсера/антибот-страницей**, а не новой пустой выдачей.

При этом:

- `seen_ads` не менять;
- ordinary snapshot не менять;
- администратору отправить предупреждение;
- дождаться следующего цикла.

Точное число 60 не используется как обязательное условие.

### 9.5. Detail-page временно не загрузился

ID не помечать как seen.

Он будет повторно рассмотрен при следующем появлении в выдаче.

### 9.6. Detail-page вернул устойчивый 404/410

Объявление можно пометить seen и больше не запрашивать.

## 10. SQLite

Использовать `database/sql` + pure-Go SQLite driver `modernc.org/sqlite`.

Один файл БД.

Для простоты:

`db.SetMaxOpenConns(1)`

### 10.1. Таблица seen_ads

```sql
CREATE TABLE IF NOT EXISTS seen_ads (
    ad_id INTEGER PRIMARY KEY,
    first_seen_at TEXT NOT NULL
);
```

### 10.2. Таблица settings

Настройки хранятся одним JSON blob, чтобы не создавать миграцию на каждое новое поле:

```sql
CREATE TABLE IF NOT EXISTS settings (
    id INTEGER PRIMARY KEY CHECK (id = 1),
    json TEXT NOT NULL
);
```

### 10.3. Таблица state

```sql
CREATE TABLE IF NOT EXISTS state (
    key TEXT PRIMARY KEY,
    value TEXT NOT NULL
);
```

Минимальные ключи:

- `initialized`
- `last_successful_poll_at`
- `previous_ordinary_ids`

Pruning `seen_ads` в MVP не нужен.

## 11. Telegram

### 11.1. Топология

- настройки изменяются администратором в **личном чате с ботом**;
- объявления отправляются в **одну заданную Telegram-группу**;
- технические ошибки отправляются администратору лично, не в группу.

Это проще и безопаснее, чем управление фильтром из группы.

### 11.2. Конфигурация

Environment variables:

```text
TELEGRAM_BOT_TOKEN
TELEGRAM_ADMIN_USER_ID
TELEGRAM_TARGET_CHAT_ID
DB_PATH
```

`DB_PATH` может иметь разумное значение по умолчанию.

### 11.3. Получение команд

Использовать Telegram Bot API long polling (`getUpdates`).

Публичный webhook/HTTPS endpoint не нужен.

### 11.4. Команды

Минимум:

- `/start` — показать меню и текущий фильтр;
- `/filter` — открыть редактирование фильтра;
- `/status` — статус сервиса.

`/status` показывает:

- время последнего успешного Somon poll;
- время следующего poll;
- количество seen ID;
- краткое представление текущего фильтра;
- состояние normal/backoff.

### 11.5. Меню фильтра

Главное inline-меню:

```text
Цена:       3500 — 6000
Комнаты:    1, 2, 3
Этаж:       2, 3, 4, 5, 14+
Автор:      <5
Минус-слова: посуточно, подселение
Тип:        Обычные + VIP

[ Цена ]       [ Комнаты ]
[ Этаж ]       [ Автор ]
[ Минус-слова ][ Тип ]
```

Комнаты и этажи — inline toggle buttons.

Автор — single-select.

Тип — toggle buttons.

Цена — бот просит текстовое значение, например:

- `3500-6000`
- `-6000`
- `3500-`
- `-` — убрать ограничение

Негативные слова — строка через запятую:

`посуточно, подселение, без детей`

`-` — очистить список.

Только `TELEGRAM_ADMIN_USER_ID` может менять настройки.

### 11.6. Изменение фильтра

Изменение фильтра действует **только на новые ID после изменения**.

Старые `seen_ads` не пересматриваются и не отправляются повторно.

Никакого retroactive backfill.

## 12. Формат Telegram-уведомления

На каждое прошедшее объявление отправляется одно сообщение.

Предпочтительно `sendPhoto`:

- Telegram получает URL первой фотографии Somon;
- сервис сам фотографию не скачивает и не хранит;
- если фото отсутствует или отправка фото не удалась — fallback на обычное текстовое сообщение.

Пример:

```text
2-комн. квартира — 5 999 c.
4 этаж · VIP

Автор: Rofi Estate R.M
Активных объявлений: 17

4 этаж, новый ремонт...
[короткий фрагмент описания]

Опубликовано на Somon: 12 минут назад
```

Inline button:

`Открыть на Somon`

В caption:

- заголовок;
- цена;
- комнаты;
- этаж;
- Обычное/VIP;
- имя автора, если доступно;
- активных объявлений автора;
- короткое описание;
- отображаемый возраст объявления.

Описание обрезать так, чтобы caption гарантированно помещался в лимит Telegram; ориентир — 400–500 символов описания.

Телефон автора не извлекать.

## 13. Go stack

Рекомендуемый минимальный стек:

- Go 1.25+;
- `net/http`;
- `github.com/PuerkitoBio/goquery`;

Не использовать browser automation.

## 14. Процесс и deployment

Приложение работает как один постоянно запущенный процесс, потому что одновременно:

- long-poll Telegram;
- ждёт очередного Somon poll.

Достаточно двух простых goroutine:

1. Telegram update loop;
2. Somon scheduler.

Без worker pool и job queue.

Deployment:

- один бинарник;
- один SQLite-файл;
- один systemd service;
- stdout/stderr → journald.

Docker не является частью обязательного решения.

## 16. Минимальное тестирование

Нужны только тесты, которые реально защищают scraper от тихой поломки.

### 16.1. HTML fixtures

Сохранить реальные HTML fixtures:

1. main category;
2. обычное detail-объявление;
3. promoted/discount detail-объявление.

### 16.2. Parser tests

Проверить:

- число найденных карточек >0;
- ID;
- current price;
- rooms;
- floor;
- promotion type;
- URL;
- first image;
- description;
- seller active ads.

Отдельный regression test: URL slug может содержать старый этаж — парсер обязан брать видимый текущий этаж.

### 16.3. Filter tests

Проверить границы:

- цена min/max включительны;
- `14+` включает 14, 15, 20;
- `<2`, `<5`, `<10`;
- `unknown`;
- ordinary vs promoted;
- простой negative substring.

Команда:

`go test ./...`

Никакого отдельного E2E-фреймворка в MVP.

## 18. Критерии приёмки MVP

MVP считается готовым, если:

1. При первом запуске текущие объявления создают baseline и не спамят группу.
2. Следующие проверки происходят через случайные 10–30 минут.
3. В нормальном цикле выполняется один GET основной выдачи плюс detail GET только для новых карточек, прошедших card-prefilter.
4. Один `ad_id` никогда штатно не отправляется дважды.
5. Поддерживаются все согласованные фильтры:
   - цена;
   - комнаты;
   - этаж;
   - число активных объявлений автора;
   - негативные слова;
   - ordinary/VIP.
6. `14+` корректно объединяет этажи >=14.
7. VIP и TOP Somon корректно объединяются в тип `VIP`.
8. Количество активных объявлений автора читается с detail-page и показывается в Telegram.
9. Негативные слова проверяются простым substring без NLP.
10. При ошибке парсинга HTML база не воспринимает страницу как пустую выдачу.
11. При 403/429 сервис не начинает частые retry.
12. После рестарта с существующей БД старые объявления не отправляются повторно.
13. Изменение фильтра не вызывает retroactive отправку старых объявлений.
14. При возможном разрыве ленты запускается максимум один recovery sweep, после чего сервис возвращается к обычному режиму.
15. Сервис устанавливается как один systemd unit и не требует браузера/Redis/PostgreSQL.

---

## 19. Известные ограничения MVP

1. Без полного обхода выдачи невозможно формально гарантировать 100% получение каждого объявления при аномально высоком churn или длительном простое сервиса.
2. Recovery существенно снижает этот риск, но не превращает систему в полный crawler.
3. «Новое» означает first-seen ID, а не доказанную исходную дату публикации.
4. Сильно криво оформленное поле остаётся `unknown`; система не пытается «догадаться».
5. Изменение DOM Somon может потребовать обновить HTML parser. Fixture-тесты и sanity check должны сделать такую поломку явной.
6. Текущие опубликованные условия Somon содержат запрет на сторонние программы/автоматизированное извлечение данных; это отдельный эксплуатационный риск.
